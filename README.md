# Photo gallery from an S3 bucket

Static site (HTML + CSS + JS, no build step, no backend) that reads the list of
photos in a folder of a public S3 bucket and shows them in a gallery with a
lightbox.

## Usage

Open the site passing the bucket folder in the `bucket-url` parameter:

```
https://<user>.github.io/<repo>/?bucket-url=https://s3.example.com/my-bucket/photos/
```

Without the parameter the site asks for the folder address to show. A default
one can be set in the `DEFAULT_BUCKET_URL` constant in `assets/app.js`. Once
the gallery is open, the folder is changed only by editing the address.

Both S3 address styles are accepted:

| style | example |
| --- | --- |
| path-style | `https://s3.example.com/my-bucket/photos/` |
| virtual-hosted | `https://my-bucket.s3.example.com/photos/` |

## How it works

1. The browser calls `ListObjectsV2` on the bucket
   (`?list-type=2&prefix=photos/`), following pagination to the end.
2. Only image files are kept from the results (`jpg png gif webp avif bmp tiff heic`).
3. Thumbnails are loaded only when they enter the viewport
   (`IntersectionObserver`).

### Bucket requirements

- **public read access to objects** (`s3:GetObject`);
- **public file listing** (`s3:ListBucket`);
- **CORS** allowing `GET` from the site's origin. Minimal rule:

```json
[
  {
    "AllowedOrigins": ["*"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["*"]
  }
]
```

If one of the three requirements is missing, the gallery shows an error
message explaining which one.

### How to make files public to use them here

The gallery reads the bucket directly from the browser, with no server in
between: it needs two public permissions and a CORS rule.

- **reading files** (`s3:GetObject`), so photos can be opened;
- **listing files** (`s3:ListBucket`), so the site knows which photos exist;
- **CORS** allowing `GET` requests from the site's origin (see the project's
  README).

**Whole bucket public.** If the provider's console offers a "public read
access" switch on the bucket, it's the simplest route: it usually enables
both reading and listing on all files.

**Only one folder, bucket private for the rest.** This needs a bucket policy
that grants the two permissions only on the folder's prefix, keeping
everything else private:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadFolder",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/photos/*"
    },
    {
      "Sid": "PublicListFolder",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::my-bucket",
      "Condition": {
        "StringLike": { "s3:prefix": ["photos/*"] }
      }
    }
  ]
}
```

Replace `my-bucket` and `photos/` with your own. Some S3-compatible providers
use a different syntax to identify buckets and objects in the resource: the
policy structure (principal, action, resource, condition) stays the same,
but check their documentation for the exact format. The CORS rule described
in the README also needs to be added.

> **Warning:** anyone who knows the address can view and list the files made
> public this way. Keep anything that shouldn't be shared out of the public
> folder.

## Previews

Original photos can weigh several MB each: loading the grid at full
resolution would use hundreds of MB. Thumbnails are therefore **always**
generated by the free public service [wsrv.nl](https://wsrv.nl) — this is not
a choice exposed to the user: a 6 MB photo typically drops below 15 KB in
WebP.

Previews are not saved either in the bucket or on the site: wsrv.nl generates
them on the fly and serves them from its own cache
(`cache-control: public, max-age=31536000`), so each photo is resized only
once.

The lightbox shows a 2400 px version (used both as the initial preview and,
until zoom reaches the original, while zooming in), and the **Download**
button always points to the original file in the bucket.

Previews are requested only when needed: nothing is prepared in advance, so
the proxy does no work for photos nobody opens. The first request for each
photo is the slowest, since it has to download the original from the bucket
and resize it; from the second request on it is served from cache. The wait
is covered by the fallback described below.

### Progressive fallback

Opening a photo whose large preview isn't ready yet immediately shows the
grid thumbnail enlarged — already downloaded, so instant — replaced with a
cross-fade by the full-size version as soon as it arrives. The two images
occupy the same grid cell and share the same aspect ratio, so the swap
doesn't shift anything. The spinner only appears if even the thumbnail isn't
available.

If the proxy doesn't respond, the site automatically falls back to the
original image from the bucket, so the gallery stays usable.

> Note: photo URLs are sent to wsrv.nl. This isn't an issue for an
> already-public bucket; for private content, change the `PROXY_BASE`
> constant in `assets/app.js` (or serve your own previews).

## Selection and bulk download

Selection mode is entered by long-pressing a photo (450 ms) or with the
**Select** button. Then: single tap to add/remove, `Shift`+click for a range,
`Ctrl`/`Cmd`+click to select without first entering selection mode, **Select
all**, `Esc` to exit. The press is cancelled if the finger moves more than
10 px, so scrolling the grid stays free.

The bar shows how many photos and how many MB are selected, with progress and
an **Abort** button during download.

### Why a ZIP and not many downloads

The `download` attribute **is ignored on URLs from another domain**: a direct
link to the bucket would open the photo instead of saving it, losing the
file name. On top of that, browsers block or drop closely-spaced programmatic
downloads.

Since the bucket sends `access-control-allow-origin: *`, the site can instead
read the bytes with `fetch()`, build the archive and save it as a `blob:` —
which is same-origin, so `download` works and the name is correct. Photos are
downloaded 3 at a time, keeping the grid order.

The archive uses the *store* method (no compression: JPEGs don't compress),
written directly in `assets/app.js` — no external library. With a single
photo selected it doesn't create a ZIP, it just saves the single file.

Limit: ZIP64 isn't implemented, so a selection is rejected above 3.5 GB with
an explicit message. Photos are kept in memory while the archive is built, so
very large selections use RAM proportionally.

For the same reason, the lightbox's **Download** button also goes through a
blob: it used to open the photo instead of saving it.

## Zoom

In the lightbox the photo is zoomed with a two-finger pinch, the mouse wheel
(or a trackpad pinch, which macOS sends as `wheel` with `ctrlKey`), and a
double tap / double click. Once zoomed in, it's moved by dragging; a double
tap returns it to full screen.

How it's built, to stay smooth:

- a single element (`.lb-zoom`, containing the stacked images) receives
  `transform: translate3d(...) scale(...)`. It doesn't touch layout, and
  `translate3d` with `will-change` keeps it on its own compositing layer;
- updates are batched in `requestAnimationFrame`: multiple move events in the
  same frame don't produce repeated work;
- during the gesture **no CSS transition**, so the photo follows the fingers
  without lag; interpolation only kicks in for the double tap;
- gestures use Pointer Events (a single logic for finger, pen and mouse) and
  `touch-action: none` on the area, without which the browser would intercept
  the pinch;
- the zoom is anchored to the point under the fingers: if `p` is the position
  relative to the center and `t` the current offset, that point stays fixed
  with `t' = p − k·(p − t)`, where `k` is the ratio between the new scale and
  the old one.

Scale is capped at 5×, and panning is constrained to the photo's edges: when
it's smaller than the viewport it snaps back to center.

### Sharpness

Zooming into the 2400 px preview holds up to a certain point, but only so
far. Past 1.4× the **original from the bucket** is downloaded, at its full
resolution, and swapped in silently: it cross-fades in above the preview,
which stays opaque underneath — the same mechanism used between thumbnail
and preview, so no flicker or jump.

It's requested once per photo and only if the user actually zooms in, so
anyone just browsing without zooming never downloads it. It's the whole file
(6.6 MB for 4592×3448 in the example), so on mobile networks the wait is
noticeable: the preview stays visible in the meantime. If the download
fails, the preview stays and the attempt can be retried.

## Gallery features

- photos sorted from oldest to newest; the order is fixed, not exposed to the
  user (change it with `state.sort` in `assets/app.js`: accepts `date`,
  `name` or `size` with an `-asc` or `-desc` suffix);
- lightbox with arrows, `←` `→` `Home` `End` `Esc` and swipe on mobile;
- direct link to a single photo via `#<key>`
  (the *back* button closes the lightbox);
- automatic light/dark theme, responsive layout.

## Publishing on GitHub Pages

The repository requires no build step. In *Settings → Pages* select
**Deploy from a branch**, branch `main`, folder `/ (root)`.
